After this page you can watch every AWS call your app makes, open one to see
what it sent and what it caused, and work with the resources behind it in a
browser.

The console is part of the doze-aws binary. It is on by default at
`http://127.0.0.1:4566/_console/`, needs nothing installed, and talks to the
services directly, so its own requests never show up as your app's traffic.

## Open it

<Steps>

1. **Start doze-aws** in your project's directory:

   ```sh
   doze-aws
   ```

   The summary it prints has a `console` line with the address.

2. **Open `http://127.0.0.1:4566/_console/`** in a browser. If you gave
   `--listen` another address, use that one, with `/_console/` after it.

3. **Make a call.** In another terminal:

   ```sh
   eval "$(doze-aws env)"
   aws s3 mb s3://uploads
   ```

   `CreateBucket` appears at the top of the wire as it happens.

4. **Click the row** to open the call beside the list.

</Steps>

`--console=false` turns the console off. It is built for windows wider than 1024 pixels; at 1024 and below it still
works and says so in the key bar, and phones are not supported.

## The wire

The console opens on the wire: every AWS call made against this endpoint,
newest first. Each row has the time, the operation, the resource it was about,
the answer and how long it took. Work that doze-aws did itself because of a
call (an S3 upload that sent a notification that invoked a Lambda) is nested
under the call that caused it, so a chain reads as one thing.

The wire keeps the last 500 calls in memory. The calls the console makes for
itself, including Connect's check, are left out, so what you see is your app.

### One call, opened

Click a row, or move to it with <kbd>j</kbd> <kbd>k</kbd> and press
<kbd>⏎</kbd>. The call opens on the right with its request id (the one the SDK
printed), the error AWS would name, and:

- **What it was sent**: the request body, with secrets masked.
- **What it caused**: the work doze-aws did because of it, when there was any.
  What your function calls from inside, with an SDK, arrives as its own call.
- **The resource it was sent to**, as a link to its page.
- **The same operation, in the ledger**: the operation's row from the
  [fidelity ledger](#the-fidelity-ledger), so you can see how much of it is
  real here.
- **Copy as curl**, built from the masked copy, so a repro you paste into a
  ticket keeps secrets out. A failed call also offers **Copy the error**.

calls that touched this queue** (or bucket, table, function).

## The map

The map draws every resource that is wired to another and the wire between
them: S3 event notifications, SNS subscriptions, EventBridge rule targets,
event source mappings, dead-letter queues and function destinations. A dark
wire carried traffic recently, and a flow a call touched in the last minute is
marked hot. Resources wired to nothing are listed underneath.

<Shot
  src={map}

Past a certain size the map stops drawing wires and shows one card per flow,
with a search box and a switch between all flows and hot ones.

## Connect

Connect shows the endpoint written four ways, each with a Copy button: an AWS
CLI profile, the environment variables every SDK reads, a Terraform provider
block, and the deploy commands for the tools you already have. Every value is
the one this instance has: the address you reached the console on, its region
and the credentials it accepts. **Run get-caller-identity** sends a real STS
`GetCallerIdentity` to prove the settings work; it does not appear on the wire.

## The fidelity ledger

An emulator has to answer a question AWS never does: is this call real here?
Every service page has an ⓘ beside its list heading. It opens the service's
ledger, **what is real here**:

- **F, functional**: real local behaviour.
- **C, cosmetic**: accepts and returns your configuration without acting on it.
- **S, stub**: an honest refusal, for something with nothing to act on locally.

Under the table, **Differences from AWS** lists where behaviour that works
still differs. The dialog reads [API support](SUPPORT.md) when you open it, so
it always matches the page. A refused call on the wire links straight to its
operation's row.

## The services

The rail on the left lists every service doze-aws serves, grouped as Storage and
data, Messaging, Compute and APIs, Config and secrets, and Stack-wide. Each has a
list of its resources, a page for one resource, and a create form where the
service has one (CloudFormation and API Gateway are filled by deploying). The
pages act on real resources: what you do here, your app sees.
