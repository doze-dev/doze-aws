# S3 — API support

Tiers: **F** = functional (real local semantics, SDK-observable behavior
matches AWS) · **C** = cosmetic (accepted and round-tripped, no local effect) ·
**S** = stub (clean error; emulating it locally would be a lie).

**All 116 documented operations are accounted for: 70 implemented, 46 refused
with a stated reason.** Nothing falls through to a different operation.

Both addressing styles (path + virtual-hosted), both SDK generations, and the
full upload-body matrix: plain, UNSIGNED-PAYLOAD, signed aws-chunked
(STREAMING-AWS4-HMAC-SHA256-PAYLOAD), and trailer-checksum streaming
(STREAMING-*-TRAILER — aws-sdk-go-v2's default). Object bodies are streamed end
to end; memory use is independent of object size.

## Sub-resource routing, and why it is guarded

S3 is the one service that cannot be audited by reading a dispatch table,
because it has none. A request is identified by method, path shape, and a
query-string sub-resource marker — `?acl`, `?tagging`, `?ownershipControls`.

The natural way to write that dispatcher is a switch on the marker with a
default arm, and **the default arm is a different operation**. An unrecognised
marker therefore does not error, it silently becomes something else:

```
GET    /bucket?ownershipControls   → (before) returned an object listing
DELETE /object?annotation          → (before) DELETED THE OBJECT
```

Both were real behaviour. The second destroys data the caller never asked to
touch.

Every marker AWS defines is now enumerated. One this build does not implement
answers `501 NotImplemented` naming the operation, and never reaches a handler
that would do something else. That is the most important guarantee on this
page, and it is what the operation counts above are measured against.

## The recurring boundary

The reason that appears most often in the stub column is **no IAM evaluation on
the S3 path**. doze-aws has an IAM service with a real policy engine, and
requests are authorized at the gateway when it is switched on — but bucket
policies, object ACLs, ownership controls and public access blocks are not
consulted by S3 itself. They round-trip so that templates and SDK code paths
that set them keep working; they do not grant or deny anything.

## Input validation

Separate from the tiers above: whether doze-aws **refuses what S3 refuses**.

| Input | Status |
|---|---|
| Bucket name — uppercase | ✅ refused |
| Bucket name — underscore | ✅ refused |
| Bucket name — shorter than 3 chars | ✅ refused |
| Bucket name — formatted as an IP | ✅ `10.0.0.1` refused; `10.0.0.256` still allowed, as in AWS |
| Everything else | not yet audited |

The IP-form case is the instructive one, and it is now closed. Validation here
was never missing — it checked case, charset and length and then **stopped
partway**, so `10.0.0.1` passed every check that existed and got a bucket AWS
would never have created. Stopping partway is harder to spot by reading than an
absent check, which is why the audit compares against AWS's own constraints
rather than reviewing the code.

The replacement is deliberately stricter than `net.ParseIP`: S3 refuses only
names that are genuinely four dotted octets, so `10.0.0.256` and `1.2.3` remain
perfectly good bucket names.
